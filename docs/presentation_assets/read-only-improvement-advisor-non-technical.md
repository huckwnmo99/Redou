# Redou Read-only Improvement Advisor

비전공자용 7페이지 발표 초안

---

## 1. 자가개선의 방식

### 프로그램이 스스로 "어디가 약한지" 발견하게 하기

Redou는 논문 PDF를 읽고, 정리하고, 검색하고, 표와 노트를 만드는 연구 작업 공간입니다.

여기서 말하는 자가개선은 프로그램이 마음대로 데이터를 고치는 뜻이 아닙니다. 먼저 현재 작업공간을 읽고, 약한 지점을 찾아서, 사용자에게 근거와 함께 알려주는 방식입니다.

```text
현재 상태 읽기
-> 약한 지점 분석
-> 개선 후보 만들기
-> 사용자가 선택
```

핵심은 자동 수정이 아니라 "근거 있는 개선 제안"입니다.

예를 들어 Redou가 이렇게 말하는 것입니다.

```text
"이 작업공간은 검색 준비가 약합니다.
먼저 embedding 누락을 확인하는 것이 좋겠습니다."
```

사용자는 최종 결정권을 그대로 갖고, Redou는 판단을 돕는 조언자 역할을 합니다.

---

## 2. 왜 이 방식을 택했나

### 안전하고 설명 가능한 방식부터 시작하기 위해

처음부터 프로그램이 자동으로 고치게 만들면 위험합니다.

논문 데이터는 사용자의 연구 맥락과 연결되어 있기 때문에, 잘못된 자동 수정은 중요한 자료를 흐리거나 없앨 수 있습니다. 또 사용 기록을 많이 모아야 하는 방식은 개인정보와 저장 부담이 커질 수 있습니다.

그래서 이번 방식은 세 가지 원칙을 택했습니다.

1. 읽기만 한다
2. 근거를 보여준다
3. 사용자가 승인해야 다음 행동으로 간다

이 방식의 장점은 분명합니다.

- 새 데이터가 많이 쌓이지 않아도 시작할 수 있음
- 기존 작업공간 상태만으로도 의미 있는 제안이 가능함
- 왜 그런 제안이 나왔는지 설명할 수 있음
- 실수해도 데이터를 바꾸지 않기 때문에 위험이 낮음

즉, Redou의 첫 자가개선은 "스스로 고치는 기능"이 아니라 "스스로 진단하고 제안하는 기능"입니다.

---

## 3. 설명: 어떻게 작동하나

### Snapshot, Analyzer, Suggestion Card

작동 구조는 세 단계입니다.

```text
Snapshot
현재 작업공간 상태를 요약한 자료

Analyzer
요약 자료를 읽고 문제 후보를 찾는 규칙

Suggestion Card
사용자가 이해할 수 있는 개선 제안
```

Snapshot은 PDF 본문이나 노트 내용을 그대로 가져오는 것이 아닙니다. 몇 개가 실패했는지, 몇 개가 비어 있는지, 어떤 상태가 누락됐는지처럼 상태 중심의 정보만 사용합니다.

Analyzer는 그 상태를 보고 패턴을 찾습니다.

예를 들어:

- 처리 작업이 오래 멈춰 있는가?
- 논문은 있는데 검색용 조각이 없는가?
- 검색 조각은 있는데 embedding이 없는가?
- 표에 빈 칸이 너무 많은가?
- 폴더나 제목 같은 기본 정리가 부족한가?

Suggestion Card에는 다음 정보가 들어갑니다.

- 무엇이 문제인지
- 어떤 근거로 판단했는지
- 왜 중요한지
- 무엇을 하면 좋은지
- 위험도와 확신도는 어느 정도인지

---

## 4. 예시 1-2: 처리와 검색

### 예시 1. PDF 처리가 멈춰 있는 경우

상황:

논문을 가져왔지만 처리 작업이 오래 queued 또는 running 상태로 남아 있습니다.

Redou가 보는 근거:

- 오래된 처리 작업 수
- 멈춘 시간 기준
- 실패한 작업 반복 여부

제안:

```text
"일부 논문 처리가 멈춘 것 같습니다.
재처리 또는 실패 원인 확인 화면을 먼저 만드는 것이 좋겠습니다."
```

왜 중요한가:

처리가 끝나지 않은 논문은 검색, 요약, 표 생성, 그림 추출에 제대로 참여하지 못합니다.

### 예시 2. 검색 가능한 데이터가 부족한 경우

상황:

논문은 있지만 검색에 필요한 chunk가 없거나, chunk는 있는데 embedding이 없습니다.

Redou가 보는 근거:

- chunk가 없는 논문 수
- embedding이 없는 chunk 수
- 영향을 받는 논문 수

제안:

```text
"검색 품질을 개선하려면 먼저 embedding 누락을 확인해야 합니다."
```

왜 중요한가:

검색 데이터가 부족하면 사용자가 질문해도 Redou가 근거 있는 답을 찾기 어렵습니다.

---

## 5. 예시 3-4: 추출과 표

### 예시 3. 논문 구조 추출이 빈약한 경우

상황:

논문에서 section, page hint, figure caption 같은 정보가 충분히 추출되지 않았습니다.

Redou가 보는 근거:

- section이 없는 논문 수
- chunk가 너무 적은 논문 수
- caption이 없는 figure 수
- page 정보가 없는 chunk 수

제안:

```text
"검색 기능을 더 늘리기 전에 PDF 추출 완성도를 먼저 점검하는 것이 좋겠습니다."
```

왜 중요한가:

논문 구조가 약하면 검색 결과, PDF 이동, 그림 보기, RAG 답변의 근거가 모두 약해집니다.

### 예시 4. 생성된 표의 근거가 약한 경우

상황:

Redou가 만든 표에 빈 칸이 많거나, 출처 근거가 부족하거나, 검증되지 않은 셀이 있습니다.

Redou가 보는 근거:

- 빈 셀 비율
- source reference가 없는 표 수
- fallback 방식으로 생성된 표 수
- 검증 실패 또는 미검증 셀 수

제안:

```text
"표 자동화를 확장하기 전에 빈 칸이 반복되는 열과 근거 부족 패턴을 먼저 확인하세요."
```

왜 중요한가:

연구 표는 신뢰가 중요합니다. 값이 있어도 근거가 약하면 사용자가 다시 확인해야 합니다.

---

## 6. 예시 5-6: 라이브러리 정리

### 예시 5. 폴더나 기본 정보가 부족한 경우

상황:

논문이 폴더에 들어가지 않았거나, 제목, 연도, 저자 수 같은 기본 정보가 비어 있습니다.

Redou가 보는 근거:

- 폴더가 없는 논문 수
- metadata가 부족한 논문 수

제안:

```text
"라이브러리 탐색이 어려워질 수 있으니 기본 metadata와 폴더 정리 후보를 확인하세요."
```

왜 중요한가:

논문이 많아질수록 작은 정리 문제도 검색, 필터링, 자동화 품질에 영향을 줍니다.

### 예시 6. 중복 논문이나 빈 폴더가 있는 경우

상황:

같은 제목과 연도를 가진 논문이 반복되거나, 비어 있는 폴더가 남아 있습니다.

Redou가 보는 근거:

- 같은 제목과 연도 조합의 중복 그룹 수
- 비어 있는 폴더 수

제안:

```text
"자동으로 합치기 전에, 중복 후보와 빈 폴더를 검토 목록으로 보여주는 것이 좋겠습니다."
```

왜 중요한가:

중복 판단은 틀릴 수 있습니다. 그래서 Redou는 바로 정리하지 않고 검토할 후보만 보여줍니다.

## 7. 현재 상태와 다음 단계

### 지금은 "분석 엔진"까지 준비된 상태

현재 구현된 것은 화면에 보이는 완성 기능이 아니라, 뒤에서 제안을 만들 수 있는 순수 분석 엔진입니다.

완료된 것:

- 작업공간 상태를 담는 Snapshot 형식
- Snapshot을 분석하는 Analyzer
- 처리, 검색, 추출, 표, 라이브러리 정리 제안
- 근거, 중요성, 추천 행동, 위험도, 확신도 형식
- 테스트와 빌드 확인

아직 하지 않은 것:

- Settings 화면에 제안 카드 표시
- 실제 앱 데이터와 연결하는 query loading
- 제안 숨기기 또는 나중에 보기
- 장기 사용 기록 저장
- 자동 수정

다음 단계는 간단합니다.

```text
기존 앱 데이터 연결
-> Settings 화면에 작은 제안 카드 표시
-> 사용자가 유용한지 확인
-> 그 다음에 저장, 알림, 자동화 여부 결정
```

정리하면, Redou의 자가개선은 한 번에 똑똑한 자동화를 만드는 방향이 아닙니다.

먼저 안전하게 읽고, 설명 가능한 근거를 만들고, 사용자가 믿고 선택할 수 있는 제안을 보여주는 방향입니다.
